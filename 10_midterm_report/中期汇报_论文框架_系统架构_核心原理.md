# 第一部分 论文整体框架（六章）

## 1.1 一句话主线
> 单向 MIPI CSI-2 链路上，坏一行不必丢/重传整帧——用**已有的低速反向通道**请求上游**只重发那一行**，

# 第二部分 系统架构

## 2.1 总体数据通路（一条主链 + 一个可靠性子系统）

```
         ┌──────────────── 数据主通路（像素流方向 →）────────────────┐
D-PHY/PPI → Lane 去歪斜/合并 → CSI-2 协议解析(短包/长包+ECC/CRC) →
         帧行同步 FSM → 像素重组(RAW8/10 · RGB888 · YUV422) →
         自适应预处理(帧统计+亮度/对比度/灰平衡) → AXI 写通路 → DDR
                                    ▲
                                    │ 错误上下文(帧号+帧内行号+VC/DT)
         ┌──────────── 可靠性子系统（创新点载体）────────────┐
         错误分类定位 → 重采集请求控制 → 写回覆盖控制 →（回注 AXI 写通路按行号覆盖坏行原槽）
                            │
              经低速反向通道 CCI/I²C ← → 上游可控图像源（重发指定行）
```

## 2.2 模块分组与职责（对应真实 RTL 文件）

| 分组 | 模块（`01_source_code/rtl/…`）| 职责 |
|---|---|---|
| **PHY 适配** | `phy_adapter/phy_digital_adapter`、`phy_adapter/mipi_dphy_ppi_adapter` | D-PHY/PPI → 数字字节流（本文数字抽象边界） |
| **Lane 处理** | `csi2_rx/lane_deskew_buffer`、`csi2_rx/lane_reorder_merge` | 去歪斜、多 lane 对齐合并 |
| **协议解析** | `csi2_rx/csi2_short_packet_parser`、`csi2_long_packet_parser`、`csi2_header_ecc_checker`、`csi2_payload_crc_checker` | 短/长包解析、**ECC 头校验（1纠2检）**、**CRC16 载荷检错** |
| **帧行同步** | `csi2_rx/frame_line_sync_fsm` | FS/FE/LS/LE 事件 → 帧/行边界；**帧内行号（每帧复位）★多帧关键** |
| **像素重组** | `pixel/raw8_unpack`、`raw10_unpack`、`rgb888_unpack`、`yuv422_unpack` | 四格式解包为像素 |

| **缓存/CDC** | `buffer/async_fifo` | 格雷码指针异步 FIFO，跨时钟域速率解耦 |
| **配置** | `reg_if/cfg_reg_if_apb`、`top/fpga_apb_boot_cfg` | APB 寄存器、上电引导配置 |
| **可靠性子系统** ★ | `reliability/err_classifier`、`err_frame_line_logger`、`packet_error_policy`、`retry_request_ctrl`、**`recapture_writeback_ctrl`**、`degrade_recover_fsm`、`resync_ctrl_fsm` | 检错定位 → 记录帧/行号 → 错误策略 → **重采集请求** → **写回覆盖（创新核心）** → 降级/重同步恢复 |
| **顶层** | `top/mipi_csi2_capture_top`、`_fpga_wrapper`、`_dphy_wrapper`、`_recap_wrapper` | 集成；recap_wrapper 暴露可控源旁路用于闭环演示 |

## 2.3 三个时钟域与 CDC
- **字节时钟域**（PHY 字节流）｜**像素时钟域**（重组/预处理）｜**AXI 时钟域**（写 DDR）。
- 跨域一律经 `async_fifo`（格雷码指针，相邻码字单比特翻转，规避多比特同步亚稳态）；式(2-1) MTBF 佐证。

## 2.4 可靠性子系统 = 创新点落地处
- **检错定位**：ECC/CRC 检出坏行 → `err_classifier` + `err_frame_line_logger` 绑定 `帧号 + 帧内行号 + VC/DT`；坏行丢弃，帧缓冲留**空槽**。
- **请求**：`retry_request_ctrl` 锁存错误上下文，经低速反向通道（CCI/I²C）向上游可控源发"重发第 N 帧第 M 行"。
- **写回覆盖（关键贡献）**：`recapture_writeback_ctrl` 三重门控 → 令 `pixel_to_axi_writer` 对重采行**按行号寻址**、
  **不推进行计数、不越界丢弃、幂等**地覆盖坏行原槽——把"只发请求"推进到"真正恢复"。

# 第三部分 核心原理：ρ=D/H 到底是什么

> 这一节从零讲清 **D**、**H**、**ρ=D/H** 三个字母，以及为什么它是全文最重要的一条边界。
> 读完你应该能对着一页 PPT 把 135× 讲出来。

## 3.0 一句话
**ρ = D/H = "往返窗口的行数" ÷ "整帧的行数"。它同时等于行级方案相对整帧方案的内存比和时延比；
ρ 越小（D≪H），行级越划算，省的倍数就是 H/D。** 代表工作点省 **135×**。

## 3.1 先建立场景：一行坏了，会发生什么？

一帧图像是**一行一行**流进来的。假设第 k 行在传输中被干扰、CRC 校验失败。你有两种粗粒度退路，和本文的细粒度做法：

| 做法 | 怎么处理坏的第 k 行 | 代价 |
|---|---|---|
| **整帧丢弃** | 整帧作废 | 内存 0，但**这一帧永久没了**（视频卡顿） |
| **整帧重传** | 让上游把**整帧 H 行**重新发一遍 | 上游要缓存**整帧**、恢复要等**约一帧时间** |
| **本文：行级重采集** | 只让上游**重发第 k 行**，回来覆盖原位置 | 上游只缓存**几行**、恢复只等**几行时间** |

问题来了：行级"只缓存几行、只等几行"——**到底是几行**？答案就是 **D**。

## 3.2 关键量 D —— 往返窗口（用"行数"量出来的反应时间）

从"发现第 k 行坏"到"重发的第 k 行到达接收端"，中间要走一个**往返**：

```
τ_rt（往返时延）= τ_det（检出坏行）+ τ_bc（请求经 CCI/I²C 传到源）+ τ_src（源定位并开始重发）
```

**但数据链路不会停下来等你**——在这段往返时间里，正常的像素流还在继续，**又流过了若干行**。
把这段往返时间换算成"流过了几行"，就是 D：

```
D = ⌈ τ_rt / T_l ⌉        （T_l = 一行的时间，即行周期）
```

**直觉**：D 就是"从发现坏行到坏行被补回来，中间隔了几行"——是这套恢复机制的**反应窗口，用行数来度量**。
- D 越小越好：检出快、反向通道快、源响应快 → D 小 → 后面所有代价都小。
- 仿真里 D≈1（检出+请求几乎一行内完成）；解析建模的保守代表值取 D=8。

## 3.3 为什么"行级只需要 D 行、整帧要 H 行"？

**关键约束（可行性条件 C1）**：上游必须把"最近发过的行"留在缓存里，等请求回来时那一行还在、能重发。
请求要 D 行的时间才绕回来，所以上游只需缓存最近 **D+1 行**（记为 `B_src ≥ D+1`）——**不是整帧**。

于是两种方案的"额外成本"天差地别：

| | 上游要缓存 | 恢复要等 |
|---|---|---|
| **行级重采集** | **D 行** ≈ `D·L` 字节 | **D 行时间** = `D·T_l` |
| **整帧重传** | **整帧 H 行** = `F = H·L` 字节 | **约一帧时间** ≈ `T_f = H·T_l` |

> 一句话：行级只需覆盖"往返窗口"这么点缓存，整帧却要把**整张图**都留着——差距就是 H 行 vs D 行。

## 3.4 ρ=D/H 的定义与三个等价含义

把上面两行相除，`L` 和 `T_l` 都约掉了：

```
内存比 = (D·L) / (H·L)   = D / H
时延比 = (D·T_l) / (H·T_l) = D / H
```

所以定义 **往返跨度比**：

```
ρ = D / H
```

它一个符号同时说了三件事：
1. **内存比**：行级缓存 ÷ 整帧缓存 = ρ；
2. **时延比**：行级恢复时延 ÷ 整帧恢复时延 = ρ；
3. **省的倍数**：行级相对整帧省 **1/ρ = H/D** 倍。

**判据**：`ρ ≪ 1`（即 D≪H，往返窗口远小于整帧）时，行级**严格更优**；`ρ→1` 时退化为整帧重传（见 3.7）。

## 3.5 代表数值：为什么是 135×

代表工作点：**1920×1080、RAW10、30 fps、D=8**。

| 量 | 算法 | 数值 |
|---|---|---|
| 行字节 `L` | 1920 × 1.25 B | 2400 B |
| 帧字节 `F=H·L` | 1080 × 2400 | ≈ **2.47 MB** |
| 行级缓存 `D·L` | 8 × 2400 | **18.75 KB** |
| **内存比 ρ** | `D/H = 8/1080` | ≈ 0.0074 → **省 135×** |
| 行周期 `T_l` | 33.3 ms / 1080 | ≈ 30.9 µs |
| 整帧恢复 `≈T_f` | — | **33.3 ms** |
| 行级恢复 `D·T_l` | 8 × 30.9 µs | **≈ 247 µs** → **省 135×** |

> **135 = H/D = 1080/8**。内存和时延都省这个倍数——同一个 ρ 的两个面。

## 3.6 更狠的一招：为什么帧级在高分辨率下"塌掉"（最有说服力）

前面比的是"单次恢复代价"。还有一层**统计层面**的碾压：

一帧有 H=1080 行，**只要有一行坏，整帧策略就得整帧重传/丢弃**。设单行残余失效概率 p，则整帧含坏行概率：

```
p_f = 1 − (1 − p)^H  ≈  H · p
```

哪怕误码率极低（BER=1e-7 → 单行失效仅 **p≈0.19%**），乘上 1080 行：

```
p_f = 1 − (1 − 0.0019)^1080  ≈  87%   ← 87% 的帧都带伤
```

后果（标称 30 fps）：

| 策略 | 有效帧率 | 为什么 |
|---|---:|---|
| 整帧丢弃 | **3.77 fps** | 只剩干净帧 `(1-p_f)=12.6%`，30×0.126≈3.77 |
| 整帧重传 | 塌到同量级 | 要多发 ~87% 的**整帧**流量，带宽撑不住 |
| **行级重采集** | **≈30 fps** | 只对**坏的那一行**反应（概率 p），**与帧高 H 无关** |

> **结论金句**：分辨率越高（H 越大），帧级越不可用——这是**结构性**的，不是调参能救的；
> 而行级开销只跟单行错率 p 挂钩、与 H 无关。这条最适合放中期 PPT 的"动机"页。

## 3.7 失效边界：ρ→1 时会怎样（能说边界才叫研究）

| 边界 | 条件 | 后果 |
|---|---|---|
| **ρ=D/H → 1** | 往返窗口 D 接近帧高 H（上游只能整帧缓存）| 行级**退化为整帧重传**（兼容，不崩）|
| 无反向通道/源不可重发 | C1、C2 不成立 | 只能退回整帧丢弃 |
| 注错密度 > 服务速率 | 单未决请求下两坏行间没完成重采 | 较早那行的请求被覆盖 → 丢失 |
| 误码过高 | 带宽余量 `h < 1/(1-p)` | 重发压垮帧率 |

> 说清"我的方法什么时候不灵、且不灵时会安全退化"，比只讲优点更显研究成熟度。

## 3.8 一页 PPT 怎么讲这个（建议排版）
- **左半**：3.1 的三行对比表（丢弃/整帧重传/行级）——抛出"粒度困境"。
- **右上**：3.2 的一张示意——坏行 k 发生后，往返期间又流过 D 行（把 D 画成一个窗口）。
- **右下**：3.5 的 135× 两行（内存 2.47MB→18.75KB、时延 33.3ms→247µs）+ 一句 `ρ=D/H`。
- **备用页**：3.6 的"87% 带伤 → 3.77fps vs 30fps"——被问"到底有多大用"时翻出来。
